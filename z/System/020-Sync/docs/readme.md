# Sync

Sync provides configurable initial loads and incremental data transfer. SQL procedures
run local copies; an external application can use the config and progress APIs
to transfer data between local or remote connections. The external application is
separate from this SQL subsystem.

## Config and execution

Create a named config with `z.usp_CreateSyncConfig`, then run it with
`z.usp_SyncOne`. A config supplies initialization and incremental queries,
the filter procedure, source and target objects, target columns, batch size and
an optional callback. Filters determine the next range and whether initialization
is needed. Copying writes batches to the configured target and records progress.
Target interfaces generated by the framework apply inserts, updates and deletes
according to the supplied keys and `___IsDeleted___` field.

Publisher APIs group configs and expose source, target and optional filter
connections, task limits, polling interval and initialization scripts to an external
application. No publisher, connection or application config is installed.
Database and Kafka configs use separate discovery APIs; Kafka processing
and offset ownership belong to the consuming application.

`z.SyncConnection` stores reusable named connection strings in plain text, without
encryption. Its identity `ConnectionID` is referenced by the nullable
`TargetConnectionID`, `SourceConnectionID` and `FilterConnectionID` columns in
`z.SyncPublisher`. Each role can share a connection row; null retains the local or
default connection behavior. Referenced connections cannot be deleted while a
publisher uses them. `z.usp_CreateSyncPublisher` accepts these IDs and remains an
insert-only helper for new publisher names. Connection rows are maintained directly.

`z.usp_SyncGetConfig` resolves the three connection IDs and returns full-length
strings using the application-facing aliases `ConnectionString` (target),
`SourceConnectionString` and `FilterConnectionString`.

`z.usp_SyncGenerateConfig` accepts an optional `@SyncMethod`, defaulting to
`RowVersion`; supported alternatives are `ChangeTracking`, `ChangeDataCapture`
and `Snapshot`. `z.usp_SyncGenerateInitializationScript` and
`z.usp_SyncCreatePublisherTable` accept the same optional method plus
`@AlternatePrimaryKey`. Caller-provided queries can implement application filters.

## Installation and dependencies

This is an initial implementation with a fresh-install baseline only; it provides no
incremental rolling-upgrade scripts or compatibility aliases.

This is a child subsystem of System at tier 020. Guarded baseline scripts define
the nine tables, then foreign keys. Functions, views and procedures follow in
the modules stage. The subsystem uses existing System catalog views, the Amazon
RDS detection function and string-printing procedure. It requires no AsyncChannel
objects. SQL Server 2019 and later is the target baseline.

CDC capture-instance names use `SchemaZSync`; CDC table storage uses the database
default filegroup. Enabling or disabling CT/CDC and running initialization scripts
are explicit operations. Initialization scripts can drop the selected target and
its related foreign keys; they stop when schema-bound dependencies reference that
target, leaving dependency removal to the caller.

## Current scope

The initial implementation preserves the existing batching, range, callback,
progress and application-facing design. Table and procedure design will evolve
separately. Runtime validation has not yet been completed. Installed SQL alone
does not establish remote-client compatibility or bidirectional conflict handling.
